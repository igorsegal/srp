\# Спецификация Модуля Бэктестинга (Replay Engine) на C++ (Версия 1.0)

\*Проект: SRP / АО Зотик. Назначение: Высокопроизводительный эмулятор рынка для честного тестирования без Look-ahead bias. Язык реализации: C++17.\*



\## 1. Философия Replay Engine

В отличие от стандартного тестера MT4, который "проигрывает" тики и свечи внутри самого терминала, наш C++ движок работает независимо. 

Он \*\*не симулирует торговлю\*\*, он \*\*симулирует поток данных\*\*. 

Задача Replay Engine — подавать данные модулям SRP строго по одному бару, гарантируя, что модуль, обрабатывающий бар `T`, физически не имеет доступа к памяти, где хранится бар `T+1`.



\---



\## 2. Архитектура классов (C++ Class Structure)



\### 2.1. `CBarData` (Структура данных)

Класс-контейнер для хранения исторических данных. Использует `std::vector` для максимально быстрого доступа по индексу (O(1)).

\*   \*\*Поля:\*\* `std::vector<long long> timestamps`, `std::vector<double> open`, `high`, `low`, `close`, `std::vector<int> volume`.

\*   \*\*Метод:\*\* `LoadFromCSV(std::string filepath)` — загружает историю в оперативную память (RAM) при старте. Это позволяет тестировать 10 лет истории за секунды.



\### 2.2. `CDataFeeder` (Подающий поток)

Это "курсор", который двигается по `CBarData`.

\*   \*\*Поля:\*\* `size\_t current\_index` (текущий бар).

\*   \*\*Методы:\*\* 

&#x20;   \*   `bool HasNext()` — проверяет, есть ли еще бары.

&#x20;   \*   `BarSnapshot Next()` — возвращает копию (или `const reference`) данных текущего бара и сдвигает `current\_index++`.

\*   \*\*Защита от будущего:\*\* `CDataFeeder` возвращает `BarSnapshot` \*\*только\*\* для `current\_index`. Модули не имеют прямого доступа к массиву `CBarData`.



\### 2.3. `CReplayEngine` (Главный движок)

Управляет циклом симуляции.

\*   \*\*Поля:\*\* `CDataFeeder feeder`, `std::vector<IModule\*> modules`, `CEventLogger logger`.

\*   \*\*Методы:\*\*

&#x20;   \*   `void RegisterModule(IModule\* module)` — подписывает модуль (Индикатор, ТР, Волны) на получение данных.

&#x20;   \*   `void Run()` — главный цикл: `while (feeder.HasNext()) { BarSnapshot bar = feeder.Next(); for (module : modules) module->OnBarClose(bar); }`



\### 2.4. `IModule` (Базовый интерфейс модуля)

Все модули системы (Indicator, TR\_StateMachine, A\_Wave\_Evaluator) наследуются от этого интерфейса.

\*   \*\*Виртуальный метод:\*\* `virtual void OnBarClose(const BarSnapshot\& bar) = 0;`

\*   \*\*Принцип:\*\* Модули не запрашивают данные сами. Движок "пушит" (`push`) им новый бар.



\---



\## 3. Защита от Look-ahead Bias в C++ (Критически важно)



В C++ легко случайно обратиться к массиву будущего (например, `close\[bar\_index + 1]`). Чтобы этого избежать, мы используем следующие архитектурные паттерны:



1\.  \*\*`const` Correctness:\*\* Модули получают `BarSnapshot` как `const BarSnapshot\&`. Они физически не могут изменить исторический бар.

2\.  \*\*Инкапсуляция истории:\*\* Класс `CBarData` хранит массивы в `private`. Доступ к ним возможен только через метод `GetBarAtIndex(int index)`, и этот метод возвращает данные \*\*только\*\* если `index <= current\_index` (проверка внутри движка). 

3\.  \*\*Событийная модель (Observer Pattern):\*\* Модуль `IndicatorProvider` не считает индикаторы "вперед". Он получает бар `T`, считает индикатор для `T` и отдает его дальше. 



\---



\## 4. Алгоритм работы (Step-by-Step)



1\.  \*\*Инициализация:\*\*

&#x20;   \*   Загрузка CSV с котировками (M1, M5, M15) в `CBarData`.

&#x20;   \*   Создание экземпляров всех модулей: `IndicatorProvider`, `BumpDetector`, `TRStateMachine`, `HypothesisTracker`, `SystemEntryValidator`.

&#x20;   \*   Подписка модулей в `CReplayEngine` в строгом порядке (Индикаторы -> Бугорки -> ТР -> Гипотезы -> Сигналы).

2\.  \*\*Цикл симуляции (Main Loop):\*\*

&#x20;   \*   Движок берет бар `T` из `CDataFeeder`.

&#x20;   \*   Движок вызывает `OnBarClose(bar\_T)` у `IndicatorProvider`. Тот считает ОЛ, СП, ЛБ и сохраняет их в `IndicatorSnapshot`.

&#x20;   \*   Движок вызывает `OnBarClose(bar\_T)` у `BumpDetector`. Тот ищет бугорки на основе `IndicatorSnapshot`.

&#x20;   \*   И так далее по цепочке до `SystemEntryValidator`.

3\.  \*\*Логирование:\*\*

&#x20;   \*   Каждый модуль, принимая решение, вызывает `CEventLogger::Log(event)`.

&#x20;   \*   В лог пишется: `Время бара (event\_time)`, `Время, когда это стало известно (known\_at = время закрытия бара)`, `Тип события` и `Цена`.

4\.  \*\*Завершение:\*\*

&#x20;   \*   Когда бары заканчиваются, движок генерирует итоговый CSV-отчет со всеми событиями и сигналами.



\---



\## 5. Оптимизация и производительность (Почему C++)



\*   \*\*Memory Pool:\*\* Вместо постоянного выделения памяти (`new`/`delete`) для каждого объекта `TR` или `Bump`, мы используем `Memory Pool` (пул объектов). Это ускоряет работу в десятки раз.

\*   \*\*Многопоточность:\*\* Разные таймфреймы (H4, H1, M15) можно обрабатывать в разных потоках (`std::thread`), синхронизируя их по времени (`std::mutex`), чтобы H1 не забегал вперед M15.

\*   \*\*STL Контейнеры:\*\* Использование `std::unordered\_map` для быстрого поиска объектов по ID (например, поиск `TR` по `tr\_id`).



\---



\## 6. Формат входных и выходных данных



\*   \*\*Вход (CSV):\*\* `Date, Time, Open, High, Low, Close, Volume`. 

\*   \*\*Выход (CSV-отчет):\*\* `event\_time, known\_at, module\_name, event\_type, price, payload`.

&#x20;   \*   Пример строки: `2026-10-30 14:00:00, 2026-10-30 14:00:00, TRStateMachine, TR\_CONFIRMED, 1.0850, potential=HIGH`.



\---



\## 7. Что этот движок даст нам на практике?



1\.  \*\*Честный бэктест:\*\* Мы сможем увидеть, сколько раз система ошиблась, и на каком именно шаге (например, из-за того, что `BumpDetector` увидел бугорок на 2 бара позже, чем нужно).

2\.  \*\*Скорость:\*\* Прогон 10 лет истории на M1 займет секунды.

3\.  \*\*Масштабируемость:\*\* Мы сможем легко добавлять новые модули (например, `NakosConstructor`) без переписывания всего движка.
